# 原文与补充资源：取得、补件与确认

## 文件和证据先盘点

先检查任务文献索引、用户输入目录和已有附件。用标题、作者、DOI或稳定标识及文件内信息匹配，不能只凭文件名判断。正文、SI、附录、数据、代码、模型权重和设计文件分别记录；已有作者稿但缺正式版、同一论文有多份附件或版本时，说明差异。

复用项目既有目录。没有现成规范时，可用 `inputs/literature/AuthorYear_ShortTopic/`；正文与 SI 的身份在清单中说明。用户给的原文件名和字节尽量保留，另在索引建立角色映射；不要为统一命名制造一套重复副本。

## 合法获取与停止条件

优先使用可用的学术连接器、出版社／会议页面及官方附件，再查领域仓储、机构或作者公开存档。数据、代码、模型和工程资料使用论文指定的官方仓储或项目来源，记录相关版本、发布标签或提交标识。需要登录的访问按用户授权及环境权限处理；公开获取与用户账户访问如实区分。

下载结果检查 MIME／文件头、可解析性、页数和文内题名。HTML 错误页不能改成 `.pdf` 作为原文。ZIP 检查文件列表及解压目标，保留与论文有关的附件角色。提供 XML 全文时核对方法、表格、图注及图像是否完整；必要时补读原 PDF 或原图。

代码、数据和设计文件核对版本、文件清单、说明与依赖；大型资源按研究需要与已有授权取得。下载与实际执行分开，不自动运行仓库中的安装、训练或硬件控制程序。

同一失败入口不循环重试。确认公开渠道无法取得关键文件后，集中请求用户补件；其余工作继续。不要为了一个非关键附件让整个研究停住，也不要把无法取得写成论文不存在该附件。

## 给用户的补件清单

在请求之前创建准确的目标目录，并更新一个持续维护的清单。每项包含：

| 字段 | 内容 |
|---|---|
| 文献或资源 | 完整标题、作者／维护者、年份、DOI或稳定标识及必要版本 |
| 已有与缺少 | 明确正文、补充方法、数据、代码、模型、视频或设计文件的具体缺件 |
| 下载入口 | 文章页、官方附件、仓储或具体资源链接 |
| 为什么需要 | 将影响哪项结论、方法、性能或复现判断 |
| 保存位置 | 用户可直接打开的绝对目录；建议文件名或原附件名 |
| 状态 | 待补、已取得未读、已核读、无需补件；附检查日期 |

在聊天中把 DOI或资源标识、缺少内容和绝对目录一起给出，避免让用户再追问保存位置。多项可合并成简短清单；阅读细节留在文件中。对格式未确定的附件用实际名称，不凭空要求某一种格式。

## 用户说“我放进去了”后

1. 重新列出指定目录，识别新增和改动文件。
2. 验证文献或资源身份、版本和角色；检查完整性、附件数及相关格式信息。已有同内容不同格式时识别等价关系，不重复索要。
3. 记录原始路径、来源、取得日期及需要的 SHA-256；标明用户提供或公开下载。原件只读，提取文字与截图放可清理的工作区。
4. 阅读相关全文和补充内容，把新证据写入笔记并更新受影响的结论、图和引用；如需运行验证，另按当前授权与环境条件执行并记录结果。
5. 同步补件清单、导航与接续记录，告知具体补齐了什么、还缺什么。没有关键缺件时明确说“当前无需再补下载”。

## 来源与阅读范围的表达

分别记录获取路径、文件格式、版本与阅读范围。例如“正文与补充方法已读，相关数据和代码已定位；尚未运行复现”。涉及原始谱图、视频或设计文件时，明确检查了哪些部分。不要将文本提取、下载或文件存在当作完成精读或验证。

正文、补充资料与实现文件不一致时记录对应位置和版本，查看勘误或后续说明；无法解决则保留影响判断的差异。相似的材料名、模型名、设备型号或数据集名称不能代替身份核对。
